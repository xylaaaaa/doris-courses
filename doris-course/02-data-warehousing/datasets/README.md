# Course Data: Historical WWI Business Data + Simulated New Orders

This course uses historical WWI business data and simulated new orders throughout historical imports, quality validation, and state updates.

| Data | Source and Purpose | Business Definitions |
| --- | --- | --- |
| `sample.json` (course bucket) | Ten historical WWI orders and related dimensions; Modules 1–4 | Pre-tax order amount 12220.60, not receipts |
| `wwi-core.tar.gz` (course bucket) | Module 5: 10 tables, 701,846 rows, approximately 16.2 MiB after extraction | Original orders, line items, customers, products, invoices, customer account transactions, and reference data |
| orders.json / orders.csv | Ten new orders generated for the course; Modules 5 and 6 | Initial amount 1400.00, with both payments and refunds at zero |

## Remote storage and local cache

The data files are not committed to this repository. `catalog.json` records the S3 bucket prefix, object sizes, and SHA-256 checksums. The course runtime downloads each object on first use into `.runtime/datasets/`, which is ignored by Git. Copy `course_secrets.env.example` to `course_secrets.env` and fill the read-only S3 credentials before the first download. Standard boto3 credentials are also supported.

The course dataset is hosted in Alibaba Cloud OSS (Hong Kong):

- Bucket: `doris-regression-hk`
- Prefix: `regression/datalake/pipeline_data/doris-course/data-warehousing/v1/`
- S3-compatible endpoint: `https://oss-cn-hongkong.aliyuncs.com`
- Region: `cn-hongkong`

The catalog contains these defaults. Copy `course_secrets.env.example` to
`course_secrets.env` and fill the credential fields before the first download.
Obtain read-only credentials for this prefix from the course maintainer.
Credentials are kept outside Git; never distribute publication credentials.
The dataset download does not require the local MinIO service. Module 4's
separate Iceberg lab still uses its own MinIO environment.

To use another bucket, set `DW_DATA_ENDPOINT`, `DW_DATA_BUCKET`, `DW_DATA_PREFIX`,
and `DW_DATA_REGION` in `course_secrets.env`. Environment variables override that
file, which overrides the catalog source. `DW_COURSE_SECRETS` selects a different
secrets file.

An existing validated cache works without network access. Set `DW_DATA_DIR` before
starting Jupyter to store downloaded files outside the checkout. To inspect a CSV:

```python
from dw_course.runtime import dataset_path
print(dataset_path("orders.csv").read_text())
```

Maintainers can publish the same release to another bucket using
[the publication script](../../../maintenance/02-data-warehousing/scripts/publish_datasets.py).
It validates every local file, leaves existing objects unchanged, and downloads
every published object to verify its hash. After publishing, update the catalog
source or supply the four location overrides; Notebook SQL does not change.

## WWI Source and Conversion

The original data is [Microsoft Wide World Importers v1.0](https://github.com/microsoft/sql-server-samples/releases/tag/wide-world-importers-v1.0),
a simulated wholesale business database generated by Microsoft.
The [original MIT license](wwi/LICENSE.txt) is retained; the [manifest](wwi/manifest.json) records the backup hash, tables and fields, file hashes, and row counts.

Historical dates remain in 2013–2016 and are not shifted to today. The core Parquet files retain every row of the selected tables, selecting only fields needed for the course;
the seventh fractional digit of datetime2 is explicitly truncated to microseconds, and computed columns are exported as values.
The ten-order sample selects orders 1–5 and 80–84; order_amount is the sum of Quantity × UnitPrice across line items,
line_count is the number of line items, and the additional projected field is data_source=WWI. This is not the turnover for two complete days.
Customers and products referenced by these orders are retained, along with customers and products 1–11 needed for the simulated new orders.

WWI customer receipts are account-level records; InvoiceID is empty for 26,637 receipt records.
They cannot be allocated as per-order payments, and negative receipts must not be treated as refunds. This backup contains no business samples of credit invoices.

## Prepare the Complete Parquet Package Locally

The small sample for Modules 1–3, simulated events, and the complete Module 5 Parquet archive are all downloaded into the local runtime cache.
On its first read, Module 5 extracts the approximately 10 MiB archive to `.runtime/wwi/` in the course directory,
then checks the sizes and SHA-256 hashes of the ten files before importing. Existing files are retained; validation mismatches stop the process and report the differences.
Modules 6 and 7 continue to read the customer and product dimensions imported by Module 5, so complete Module 5 before moving on to the quality and state Labs.

If you have already saved the same version of the Parquet files separately, you can also run the following from the repository root:

```bash
.venv/bin/python maintenance/02-data-warehousing/scripts/prepare_wwi.py \
  --source /absolute/path/to/wwi-parquet
```

The script validates the ten files and copies them to this course's `.runtime/wwi/`. If a file with the same name already exists in the destination directory, the script stops and prompts you to use a new directory to preserve existing data.
Alternatively, set DW_WWI_DATA_DIR to the directory of extracted files before starting Jupyter; this path is on the machine running the kernel.
The Lab reads local Parquet files directly and checks their integrity against the course manifest.
If files are missing, Module 5 stops before rebuilding tables.

See the [WWI Validation Record](../../../maintenance/02-data-warehousing/WWI-VALIDATION.md) for the steps to rebuild the author's export package from the official backup.
Because Parquet encoding may vary with tool versions, the manifest must also be updated when releasing a new package; validation failures must not be ignored.
When distributing the package to learners, include this document, the manifest, and Microsoft's license.

## Simulated New Order Contract

- The source is COURSE_SIMULATION, with order IDs 900001–900011, separate from historical WWI data.
- The initial 10 orders reference WWI customers/products 1–10; the 11th order references customer/product 11.
- Prices, EAST/WEST regions, and events in 2026 are teaching assumptions, not WWI's actual geographical attributes or history.
- Simulated events use Asia/Shanghai; the fixed quality cutoff is 2026-01-02 12:00:00 and does not indicate actual ingestion freshness.
- event_version is a teaching version that increases per order, not a Binlog position or timestamp.
- Redeliveries with the same event_id have identical business fields. delivery_id is a delivery identifier, not a logistics tracking number.
- The initial snapshot retains event IDs S1001…S1010, while order IDs are separately 900001…900010; the two identifiers do not need to be equal.

900001 goes through payment, shipment, and receipt to reach DELIVERED; 900003 goes through payment, cancellation, and refund to reach REFUNDED;
900002 is canceled without payment, and the other orders remain CREATED. Delivery deliberately sends the receipt event first to test out-of-order resolution.

After replay: 11 current orders with an amount of 1510.00 and 18 logical history records; cumulative payments of 250.00 and refunds of 150.00,
with net receipts of 100.00. One delivery before interruption plus two rounds of nine deliveries gives 19 raw deliveries in total.
Payments, refunds, shipments, and item details are stored in separate business tables; repeated writes are deduplicated using their respective stable IDs.
Simulated events are downloaded into the local cache and written by the Lab in the specified order to practice version-based resolution and replay reconciliation.

Simulated order CSV column order:

```text
order_id,customer_id,order_amount,status,event_version,event_id,event_time,paid_amount,refund_amount,region,data_source
```
